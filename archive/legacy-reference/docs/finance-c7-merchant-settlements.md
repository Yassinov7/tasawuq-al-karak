## مصدر الاستحقاق ومنع ازدواج C4

C4 يرحل عند التسليم أصلًا:

- مدين customer_advance بكامل المبلغ.
- دائن merchant_sales_payable بصافي كل تاجر، مجمعًا حسب merchant_id.
- دائن commission_revenue بإجمالي العمولة.
- دائن delivery_revenue برسوم التوصيل النهائية.

لا تعيد C7 هذا القيد ولا تنشئ حدث استحقاق مالي آخر. `merchant_delivery_positions` تفصيل immutable لكل SUB، يعيد استخدام قيد C4 السابق ويحفظ القيمة والنسبة والعمولة والصافي ومعرف حدث التسليم.

أضيف trigger مؤجل على `delivery_collection_results`. تنادي C4 دالة تأجيل الامتدادات قبل إدخال النتيجة؛ C7 يحتفظ بتأجيل قيد C6 ويضيف تأجيل التفصيل، حتى يقرأ عملية C4 المكتملة وقيدها المرحل عند SET CONSTRAINTS ALL IMMEDIATE قبل عودة RPC. فشل التفصيل يرد معاملة التسليم كاملة ولا يترك استحقاقًا غير قابل للمطابقة.

تتحقق C7 من: تسليم SUB فعلًا، استبعاد rejected/cancelled، مطابقة بضائع C3 الحالية والنسبة المثبتة، مطابقة ائتمان كل تاجر وإجمالي العمولة ورسوم التوصيل ومدين advance وعدد السطور في C4. لا محاسبة على السعر الأصلي بعد رفض متجر.

تعيد Migration قراءة نتائج C4 الموجودة لتكوين تفصيل metadata فقط؛ لا مالية جديدة ولا نقل تلقائي من legacy. التفرد store_order_id يجعل تكرار القراءة لا يعيد الاستحقاق. فشل مطابقة أي نتيجة قديمة يوقف الترحيل لمراجعة المالك؛ لا قيم تقديرية أو backfill مالي.

## العمولة والدقة

`commission = round(delivered_goods * frozen_commission_rate / 100, 2)`، وهي نفس معادلة snapshot السابقة. `net = delivered_goods - commission`.

تُقرأ العمولة المثبتة وتُقارن بالمعادلة، ولا تُستبدل بقيمة من الخطة الحالية. لا رسوم توصيل أو اشتراك في الأساس. نسبة حتى أربع منازل، مبلغ SYP رئيسي حتى منزلتين. numeric في SQL، ونصوص وBigInt في التطبيق. التقريب عند حساب العمولة النهائي فقط (HALF-UP للمبالغ الموجبة). مثال 100.50 ×10%=10.05، الصافي90.45؛ و0.05×10%=0.01.

الصافي الصفري يبقى سجلًا تشغيليًا، ولا يُضاف إلى SET صفرية. إذا كانت العمولة100%، يظل C4 مصدر إيراد العمولة ولا ينشأ payable صفري. رفض متجر لا يولد له صف تسليم أو عمولة مكتسبة. التسليم الصفري لا يولد قيدًا ماليًا جديدًا.

## SET وPAY

الجداول الجديدة منفصلة عن legacy:

- merchant_settlement_documents: SET معدة immutable.
- merchant_settlement_document_items: كامل صافي SUB لكل بند، وتفرد SUB عبر جميع SET.
- c7_merchant_settlement_payments: PAY واحد لكل SET.

توسعت روابط financial_document_references بـFK لكل SET/PAY، مع إبقاء ORD/SUB/DLV/TXN/RCT وPAY أجور C6 سليمة. الترقيم C2 نفسه، ولا قطع بعد ست خانات.

`prepare_c7_settlement(target_store,expected_user,attempt_key,target_subs,expected_amount)`:

- admin + تفويض may_prepare، ومقارنة JWT، وقبول إعداد التسويات مفعّل.
- قفل المتجر، ثم محاولة C2 بمدخلات canonical ثابتة (SUB مرتبة وغير مكررة).
- حتى100 SUB مسلمة، موجبة، للتاجر/المتجر نفسه، وغير محجوزة مسبقًا.
- المجموع محسوب خادميًا؛ expected_amount للمقارنة فقط.
- SET وبنود ومرجع فقط، دون حدث أو قيد نقدي.

`pay_c7_settlement(target_store,target_settlement,expected_user,attempt_key,expected_amount)`:

- admin + تفويض may_pay مستقل عن may_prepare وعن تفويضات C5/C6.
- قفل المتجر أولًا، ثم **نفس finance_private.c6_treasury_mutex**، ثم SET.
- READ COMMITTED مطلوب؛ الرصيد من سطور C2 المرحّلة وعمليات مكتملة، لا خزينة legacy ولا قيمة mutable.
- يثبت كامل SET فقط بعد التأكيد الفعلي من الموظف؛ لا صرف جزئي في هذه المرحلة.
- مدين merchant_sales_payable للتاجر / دائن treasury_cash بالمبلغ نفسه.
- لا سطر driver_cash، ولا خصم أجر أو اشتراك.
- PAY/حدث merchant_settlement_paid/قيد/نتيجة ضمن معاملة واحدة، وفحص مؤجل يفرض اكتمالها.
- مفتاح مختلف لنفس SET المدفوعة يعيد النتيجة السابقة دون ترحيل آخر؛ المدخلات المختلفة بالمفتاح نفسه ترفضها C2.

حالة SET مشتقة من وجود PAY؛ لا عمود رصيد أو حالة مالية mutable. المبلغ قيد التسوية هو SET غير المصروفة. المتاح = صافي المستحق − المصروف − المحجوز. فحص رصيد حساب التاجر يشمل جميع متاجره ويقارنها بمستندات C4/C7؛ الحركات غير المصنفة والعكس والتعارض يوقفون الإعداد والصرف للمراجعة، دون تصحيح مالي صامت.

الإعداد والصرف مغلقان افتراضيًا، والتفويضات فارغة. إيقاف قبول SET جديدة مستقل عن السماح بصرف SET معدة سابقًا. لا يوجد إلغاء أو تحرير حجز SET في هذه المرحلة؛ لا يُعاد استخدام SUB تلقائيًا. إضافة عقد إلغاء مدقق أو صرف جزئي لاحقًا تحتاج مرحلة مستقلة، ولا يلزم افتراضها لإكمال C7 الحالية.

## المنافسة والصلاحيات

C6: قفل السائق ثم mutex الخزينة. C7: قفل المتجر ثم mutex الخزينة. لا مسار يعكس ترتيب الطرف/الخزينة. C5 إضافة نقد فقط، فلا تحتاج قفل الصرف العام؛ إذا التزم قبض متزامن بعد قراءة الصرف قد يرفض الصرف لنقص مؤقت، لكنه لا يستبق قبضًا غير مؤكد. أي مخرج C2 مستقبلي للخزينة ملزم بالتسلسل نفسه.

RLS يفصل المتاجر عبر stores/merchants.owner_user_id. لا كتابة مباشرة للأدوار التشغيلية. RPC يطابق expected_user مع auth.uid قبل أي كتابة أو استعادة. قائمة الإدارة admin فقط، والتاجر يقرأ متجره فقط؛ لا RPC قراءة عامة لطلبات الآخرين. لا helper خاص داخل policy يحتاج منح finance_private للمستخدم. جميع دوال SECURITY DEFINER بمسار بحث فارغ، وامتيازات الدوال الخاصة مسحوبة من anon/authenticated/service_role.

أرقام السجل لا تُعرض كصفر عند فشل التحميل. نطاق القراءة موسوم بالحساب والمتجر والصفحة. المحاولات محفوظة دائمًا لكل موظف ومتجر، بمدخلات ومفتاح ثابتين. بعد فقد الاستجابة تُقرأ النتيجة أولًا، ولا تعاد عملية غامضة بمفتاح مستقل. نتيجة نهائية تبقى حتى إنهائها صراحة. نجاح الصرف لا يُعاد وصفه كفشل إذا فشلت قراءة الشاشة اللاحقة.

## الاختبار المعزول

لم تُنفذ SQL أو JWT أو اختبارات التزامن في هذه الجولة؛ لا PostgreSQL/psql جاهز محليًا. لا يجوز تشغيل أدوات الاختبار على Supabase الأساسي.

الأداة لا تطبق migrations. المتطلبات التي يجهزها المالك على قاعدة محلية disposable كاملة المخطط:

1. المراحل السابقة ثم C4 المعدلة وC5 وC6 وC7 بالترتيب. لا تعديل تاريخي.
2. manifest C2 المحمي: loopback رقمي، اسم ينتهي `_c2_test`، OID ومعرفcluster وعلامةtoken، مسارpsql مطلق ومثبت، ومستخدمون اصطناعيون فقط.
3. ثلاثة منتجات C3 في متاجر مختلفة، وسائقان معتمدان، وتاجران بمالكين مختلفين ونسب اشتراك حالية مختلفة وأقل من100%، ومنتجات موجبة الصافي. غياب fixture يسبب فشلًا لا تخطيًا.
4. تسلسل C4 ثم C5 ثم C6 الاختباري كما في توثيقها، مع C7 مضافة للمخطط؛ C7 لا تزيد عدد قيود C4/C6.
5. إبقاء C7 مغلقة ومجموعة SET فارغة، وتعيين C2_TEST_DATABASE_URL وC2_TEST_MANIFEST وC2_ALLOW_DISPOSABLE_TEST=yes وC7_ALLOW_DISPOSABLE_TEST=yes.
6. ينفذ المالك `node scripts/test-finance-c7-postgres.cjs` على تلك القاعدة فقط. كل اتصال يتحقق من الهوية قبل أي SQL.

SQL تختبر التسليم المفرد والمتعدد والرفض والصفر، ثبات النسبة، تطابق القيد، SET متعددة SUB، عدم ازدواج الإعداد، التفويض المستقل، الفشل الفوري والمؤجل والتراجع، والاستعادة وRLS الفعلية عبر SET ROLE وclaims محلية. لا تعتبر قراءة صفوف صفر كإثبات RLS: يتأكد الاختبار أيضًا من ظهور صفوف المالك ومن عدم ظهور متجر أجنبي معرف مسبقًا.

الأداة اللاحقة تختبر COMMIT حقيقيًا ومعاملات متداخلة، وتثبت انتظار الاتصال الثاني عبر pg_blocking_pids: سباق إعداد SET، سباق صرف نفس SET، وC6 مقابلC7 على نقد يكفي أحدهما فقط. تستهلك fixture مصروفًا اصطناعيًا من حساب موجود لإعداد حالة التنافس، داخل قاعدة الاختبار فقط. لا تنظف السجلات؛ تبقى الآثار الاصطناعية، وقد تزيد sequences حتى في rollback. إذا فشلت الأداة قد تبقى flags في قاعدة الاختبار مفعلة؛ ليست أداة نشر أو تنظيف.

يبقى مطلوبًا: تشغيل الاختبارات فعليًا، JWT موقع عبر PostgREST، مراجعة الصلاحيات بعد التطبيق، توليد الأنواع من مخطط مطبق ومقارنتها بالعقود اليدوية، واختبار الهاتف والثيم والعودة وتبديل الحساب وفقد الشبكة. لا يعتبر النجاح المحلي اعتمادًا لهذه الاختبارات.
