# C9 — الخزينة المركزية والعمليات المالية المعتمدة

## الحالة وحدود التنفيذ

C9 مكتملة محليًا للمراجعة: **READY FOR OWNER REVIEW**، وليست إذن تطبيق أو تفعيل. لا اتصال بـSupabase ولا SQL بعيد ولا تشغيل تطبيق. لم تُعدّل C2 أو أي migration مطبقة. C9 وفتح إصدار الافتتاحي مغلقان افتراضيًا؛ صلاحيات العمليات الحساسة false وجدول تعريف المالك فارغ.

ترتيب C9 بعد السلسلة C2–C8 المحلية المتوافقة:

1. `20261112000100_finance_c9_treasury.sql`: القراءة والجرد وRLS وجسر قفل C5.
2. `20261112000200_finance_c9_posting.sql`: الحسابات المعتمدة والطلب والاعتماد والصرف والتصحيح والافتتاحي.

كلاهما غير مطبق. يجب اختبارهما مع C4–C8 ومشغلاتها المؤجلة على PostgreSQL معزول. نجاح المصدر أو TypeScript لا يثبت ذلك. المسارات القديمة `expense_request/opening_request` في RPC الرقابة ترفض الكتابة بـ0A000 وتوجه إلى سير العمل المالي؛ لا توجد طلبات رقابية وهمية قابلة للصرف.

## الحسابات ووحدة المال

مصدر الرصيد الوحيد: مجموع مدين `treasury_cash` ناقص دائنه في قيود C2 المرحّلة والعمليات المكتملة. لا عمود رصيد mutable، ولا استيراد legacy. جميع المبالغ SYP رئيسية exact numeric بمنزلتين؛ التحقق يرفض الدقة الزائدة ولا يقربها. التطبيق يستخدم strings وBigInt للتطبيع والعرض، ولا يحسب المبالغ المالية بـNumber.

أضيفت تعريفات system فقط:

- `office_operating_expense`: expense، مصروف تشغيل المكتب.
- `treasury_cash_shortage_expense`: expense، مصروف نقص الخزينة.
- `treasury_cash_overage_income`: income، إيراد زيادة الخزينة.
- `opening_balance_equity`: equity، مقابل الافتتاحي.

C2 يستخدم نص account_type بقيد CHECK، لا ENUM. الترحيل الثاني يوسع القيد المحدد `financial_account_definitions_account_type_check` ليشمل equity ويحافظ على الفئات القديمة وجميع الصفوف. لم تتغير دوال التوازن أو الحسابات القديمة؛ لا يوجد استخدام آخر لـaccount_type داخل migrations الحالية يفترض أربع فئات فقط. لا يُصنف الافتتاحي إيرادًا. الفشل عند غياب القيد المتوقع مقصود بدل حذف قيود عشوائية.

## مصدر الحقيقة وحركة C5–C9

- C5: طلب تسليم عهدة لا يدخل الخزينة؛ RCT المؤكد فقط: مدين خزينة / دائن عهدة السائق.
- C6: استحقاق الأجر لا يصرف نقدًا؛ PAY فقط: مدين مستحقات السائق / دائن خزينة.
- C7: SET لا يصرف؛ PAY فقط: مدين مستحقات التاجر / دائن خزينة.
- C8: SIN ذمة وإيراد محاسبي، لا نقد؛ RCT فقط: مدين خزينة / دائن ذمم الاشتراك.
- C9: طلب المصروف واعتماده لا يصرفان؛ تأكيد الصرف فقط: مدين `office_operating_expense` / دائن `treasury_cash`، مرجع PAY + مرجع قيد TXN.
- نقص الجرد: مدين `treasury_cash_shortage_expense` / دائن خزينة؛ زيادة الجرد: مدين خزينة / دائن `treasury_cash_overage_income`، مرجع ADJ + TXN.
- افتتاحي: مدين خزينة / دائن `opening_balance_equity`، مرجع ADJ مستقل + TXN. لا قيد صفري ولا ذمة شخصية على الموظف.

لا تعيد C9 إثبات أي استحقاق أو قبض من C4–C8، ولا تجري مقاصة. السجل يشمل القيود العكسية بإشاراتها الفعلية. الأرصدة شاملة حتى Snapshot القراءة؛ فلتر الفترة يؤثر على المقبوضات والمدفوعات وصافي الحركة فقط. الرصيد التراكمي يُحسب قبل الفلاتر وpagination، بترتيب حتمي كامل وليس انطلاقًا من صفر لكل صفحة.

## المستندات وحالاتها

`treasury_control_documents`: سجل الجرد append-only مع الرصيد والمعدود والفرق ونقطة القطع والمؤلف والسبب. الجرد والمراجعة وحدهما لا ينشئان قيودًا.

`treasury_finance_requests`: طلب ثابت (نوع، مبلغ، سبب، مؤلف، وقت؛ نوع المصروف أو مصدر/تاريخ الافتتاحي أو مرجع الجرد).

`treasury_finance_events`: أحداث approved/posted/rejected مستقلة لا تعدّل الطلب الأصلي. الحالة مشتقة من الأحداث وليست عمود رصيد أو حالة قابلة للتعديل.

`treasury_finance_postings`: إثبات ترحيل واحد لكل طلب، وواحد لكل فرق جرد، وافتتاحي واحد للخزينة مدى عمر السند حتى لو عُكس لاحقًا. يرتبط بعملية C2 ومرجع PAY/ADJ وحدث مالي وقيد متوازن. تحقق مؤجل يشترط العملية المكتملة والقيد الأصلي وطرفيه الفعليين ومبلغهما وحساباتهما المعتمدة.

- requested: طلب فقط، لا مال.
- approved: اعتماد المصروف فقط، لم يصرف بعد.
- posted: تأكيد صرف المصروف، أو اعتماد وترحيل تصحيح/افتتاحي ذريًا.
- rejected: قرار رفض موثق، لا مال.

اعتماد التصحيح/الافتتاحي ينشئ حدث approved ثم posted في المعاملة نفسها. رفض طلب معتمد/مرحّل غير مدعوم؛ أي إلغاء أو عكس مالي لاحق يحتاج عملية مستقلة ولا يمس الأصل. لا توجد واجهة عكس أو انتقال مالي جديد ضمن C9.

## الفصل بين الصلاحيات

كل العمليات تتطلب admin **وتفويضًا خادميًا مستقلًا** في finance_private.c9_permissions، ولا يوجد setter عام:

- expense: طلب مصروف؛ expense_approve: اعتماده أو رفضه؛ pay: تأكيد الصرف.
- count_cash: إجراء الجرد؛ adjust_request: طلب تصحيح؛ adjust: اعتماده/رفضه.
- opening: طلب افتتاحي؛ opening_approve: اعتماد/رفض افتتاحي، بالإضافة إلى هوية مالك مسجلة في finance_private.c9_system_owners.
- dashboard وledger للقراءة؛ review لمراجعة الجرد الرقابية السابقة دون تصحيح.

لا يستطيع مقدم الطلب اعتماده. معتمد التصحيح يجب أن يختلف أيضًا عن مجري الجرد. لا يُشترط شخص ثالث لصرف المصروف بعد اعتماد مستقل، لكن منفذ الصرف يحتاج pay صراحةً. هذا لا يتيح له اعتماد طلبه بنفسه.

الافتتاحي يتطلب owner_confirmed=true عند الاعتماد وهوية مالك خادمية، لا مجرد مربع في التطبيق أو role=admin. يُدخل مالك قاعدة البيانات هوية المالك الحقيقي وسبب توثيقها خارج واجهات التطبيق، بعد المراجعة. لا تدرج migration أي مستخدم تلقائيًا. لا يمكن للمستخدم تعديل تلك الهوية أو منح الصلاحيات عبر RPC/Storage.

RLS على الجداول الجديدة، SELECT بحسب التفويض المالي، ولا DML مباشر لـanon/authenticated/service_role. جميع الدوال الحساسة SECURITY DEFINER مع search_path فارغ وGRANT/REVOKE صريح؛ finance_private محجوب. صلاحية طلب مصروف وحدها لا تكشف رصيد المكتب؛ الرصيد يعاد للمفوض باللوحة أو السجل أو الصرف.

## الجرد والتصحيح

جلسة واحدة مفتوحة، ثم مبلغ معدود فعليًا. يتم أخذ `c6_treasury_mutex` وSnapshot جديد بعد انتظار أي حركة سابقة، ومقارنة بصمة **مجموعة سطور الخزينة** مع البداية، لا مقارنة صافي الرصيد فقط. أي قبض/صرف أو عكس يلغي صلاحية الجلسة حتى إن عاد الرصيد إلى الرقم نفسه.

طلب التصحيح يقرأ المبلغ والإشارة من نتيجة الجرد الخادمية فقط؛ لا يقبل amount من التطبيق. يعيد التحقق من البصمة عند الطلب وعند الاعتماد تحت القفل نفسه. إذا تحرك النقد، ترفض العملية بـstale_count ويجب إعادة الجرد، ولا تُرحّل تسوية تخمينية. التحقق المؤجل يعيد تركيب نقطة القطع باستثناء سطور عملية التصحيح نفسها.

يمكن رفض الطلب القديم ثم تسجيل طلب مرتبط بجرد جديد. لا يمكن تصحيح الفرق المرحّل نفسه مرتين حتى بمفاتيح أو موظفين مختلفين. مراجعة فرق دون ترحيل لا تعني أنه سُوي. لا يُفترض أن النقص دين على مجري الجرد.

يجب إيقاف المناولة النقدية الفعلية أثناء العد؛ قاعدة البيانات تضبط نقطة القطع المحاسبية ولا تثبت عد الأوراق أو تمنع حركة مادية غير مسجلة. لا تُحتجز معاملة طوال العد البشري. يمكن لمفوض جرد آخر إلغاء جلسة مهجورة بسبب موثق، لكنه لا يكمل عدّ جلسة غيره.

## المصروف والافتتاحي

المصروف: مبلغ موجب ثابت + نوع مصروف تشغيل + سبب، ثم اعتماد مستقل، ثم تأكيد تسليم النقد فعليًا. الرصيد غير محجوز عند الطلب/الاعتماد؛ يعاد فحصه لحظة الصرف تحت القفل. إذا لم يكفِ يبقى الطلب approved ويمكن صرفه لاحقًا بمحاولة جديدة بعد توفير نقد؛ لا ينشأ أثر جزئي أو رصيد سالب.

الافتتاحي: مبلغ موجب، مصدر، تاريخ نقد تقويمي صحيح لا يتجاوز تاريخ الخادم UTC، وسبب. التاريخ توثيقي؛ ترحيل C2 بوقت الخادم الحالي، لا إعادة كتابة تاريخ الدفتر. الطلب لا ينشئ مالًا. الإصدار يحتاج enabled وopening_enabled، وهما false افتراضيًا، وموافقة المالك بحساب مختلف عن الطالب. يشترط غياب **كل الحركات النقدية السابقة** وليس كون صافي الرصيد صفرًا فقط، عند الطلب وعند الاعتماد. يوجد فهرس فريد لافتتاحي واحد، ولا يعاد فتحه بعد العكس. إذا بدأت الحركات، يلزم انتقال مالي مستقل معتمد؛ ليس في هذه المرحلة.

## الأقفال والاستعادة

قفل واحد `finance_private.c6_treasury_mutex` لكل قبض/صرف/تصحيح/افتتاحي وجرد في READ COMMITTED. جسر C9 يربط C5 عند إدراج confirmed بعد أقفال السائق والطلب؛ C6 يقفل السائق ثم الخزينة، C7 المتجر ثم الخزينة، C8 التاجر بـNO KEY UPDATE ثم الخزينة والفاتورة. C9 لا تطلب أقفال هؤلاء بعد الخزينة.

begin_operation يجمد المدخلات والمفتاح والمؤلف. التكرار بنفس المفتاح يعيد النتيجة؛ محتوى مختلف بنفس المفتاح مرفوض. مفتاح مختلف لطلب مرحّل يعيد السند نفسه، ولا ينشئ قيدًا جديدًا. تفرد الطلب/الجرد/الافتتاحي يمنع ازدواج الحدث الاقتصادي مستقلًا عن مفتاح المحاولة. تُفرغ جميع القيود المؤجلة قبل نجاح RPC؛ أي فشل يتراجع معه الاعتماد والترحيل والأحداث والنتيجة كلها.

التطبيق يخزن intent قبل الإرسال ويستخدم namespace مستقلًا `treasury-finance:v1`، يتحقق من المستخدم قبل الشبكة وبعدها، ويحافظ على المدخلات عند unknown. لا يعيد إرسال مبلغ جديد ولا يعد timeout إثبات فشل. الاستعادة عبر recover_treasury_action تتحقق من صاحب العملية.

## التطبيق والملفات

- `src/lib/treasury-finance.ts`: DTO يدوي موثق، تطبيع exact، استدعاء RPC والاستعادة.
- `src/components/admin/TreasuryFinanceWorkflow.tsx`: المصروفات والتصحيح والافتتاحي، المراحل والموافقات وسجل المؤلف والوقت والمراجع.
- `TreasuryControl.tsx`: يركب سير العمل داخل تبويبات المصروفات والفروقات والافتتاحي، ويحافظ على لوحة الخزينة والسجل والجرد. لا تغيير Layout/Header/BottomNav.
- التحديث عند التركيز وبالزر وpoll كل15 ثانية أثناء التركيز، دون افتراض publication جديدة.
- لا صفر بديل عند الخطأ؛ لا عرض approved على أنه cash. زر اعتماد افتتاحي لا يظهر إلا لمن أعاد الخادم له قدرة الاعتماد، ويبقى معطلًا عند إغلاق بوابته.
- المخطط الجديد غير مطبق؛ الأنواع اليدوية لا تُسمى أنواع Supabase مولدة. التوليد الرسمي بعد تطبيق المالك والتحقق، بإذن اتصال مستقل.

## اختبارات PostgreSQL المعزولة — غير منفذة هنا

الأدوات لا تطبق migrations ولا تنشئ مستخدمين ولا تنظف البيانات. تتطلب PostgreSQL موجودًا مسبقًا وقاعدة numeric-loopback منتهية `_c2_test` وعلامة c2_test_guard، وmanifest مثبت OID/system identifier/token ومسار psql مطلق. تفشل عند نقص fixtures ولا تتخطاها.

`manifest.c9Completion`: approver وowner، مستخدمان admin اصطناعيان مختلفان عن fixtures.admin وعن بعضهما. باقي fixtures القياسية من حارس C2. لا تستعمل حسابات حقيقية.

شغّل على حالتين معزولتين منفصلتين، لأن اختبار افتتاحي COMMIT يترك سندًا دائمًا اصطناعيًا:

1. opening: خزينة بلا سطور سابقة ولا postings C9. يشغّل `finance_c9_opening.sql` داخل rollback، ثم طلبين واعتمادين متزامنين بحدود COMMIT فعلية؛ واحد فقط يرحّل. يشمل الملكية، تأكيد المالك، إغلاق البوابة، self-approval، equity، الاستعادة، التاريخ ومنع الافتتاحي بعد الحركة.
2. operations: نقد اصطناعي مرحّل >=10.50 لاختبارات rollback، وfixtures.c9 من أداة C9 الأولى: handover غير مؤكد، subscriptionInvoice غير محصلة + subscriptionMerchant، wageTask مستحق قابل للصرف، settlement غير مصروفة. يلزم نقد فعلي كافٍ لصرف C6 وC7 مع بقاء0.02 على الأقل؛ لا تعدّل أي رصيد.

```powershell
$env:C2_ALLOW_DISPOSABLE_TEST='yes'
$env:C9_COMPLETION_ALLOW_DISPOSABLE_TEST='yes'
$env:C2_TEST_MANIFEST='C:\absolute\disposable-manifest.json'
$env:C9_TEST_SCENARIO='opening' # ثم operations على الحالة المعزولة المناسبة
node scripts/test-finance-c9-completion-postgres.cjs
```

C2_TEST_DATABASE_URL يخص القاعدة المعزولة فقط، ولا يُطبع. identity assertion في كل اتصال قبل أي اختبار. تختبر operations المصروف الفعلي وعدم الصرف عند الطلب/الاعتماد، الدقة، نقص/زيادة الجرد وحساباتهما الفعلية، الاستعادة، الصلاحيات، RLS وتمثيل claims، والقيد المؤجل المحقون والتراجع الكامل. المشغلات تُفرغ ولا يكتفى بقراءة صف قبل COMMIT.

أداة التداخل تشاهد pg_blocking_pids قبل السماح بالـCOMMIT: C5/C8 مع الجرد، C6/C7 مع مصروف يستنفد الرصيد، مصروف مع تصحيح نقص قديم، ومحاولتا صرف للسند نفسه. تبقى السجلات الاصطناعية للتدقيق وتغلق البوابات في finally. لا يُدّعى أن C9 يمكن تفعيلها عن بعد بناءً على ذلك قبل تشغيله فعليًا. rollback لا يعيد sequences؛ لا تشغّل هذه الملفات على المشروع الأساسي.

## JWT حقيقي — تجهيز منفصل وغير منفذ

`scripts/test-finance-c9-jwt.cjs` يقبل HTTP numeric-loopback فقط، ويربط API بسجل ثابت في قاعدة الاختبار المثبتة قبل أي كتابة HTTP. يتطلب Local Auth/PostgREST موجودين مسبقًا (لا تثبيت أو تشغيل خدمة تلقائيًا) ومستخدمين اصطناعيين حقيقيين وJWT لكل دور:

- C9_TEST_API_URL، C9_TEST_ANON_KEY المحلي العام فقط؛ لا service-role.
- C9_TEST_JWT_ADMIN / APPROVER / OWNER / NO_PERMISSION / DRIVER / CUSTOMER / MERCHANT.
- manifest.c9Jwt.request: طلب مصروف ثابت في القاعدة المثبتة يخص fixtures.admin، وnoPermissionAdmin: admin بلا أي تفويض C9.
- يفحص Auth /user ثم profiles.role لكل توكن؛ لا يثق بفك JWT محليًا. يلزم إعداد تفويض الطلب والاعتماد للـADMIN لاختبار حظر self-approval، والاعتماد والصرف للـAPPROVER، وتعيين OWNER وتفويضه، دون تفويض NO_PERMISSION.
- C9 مفعّل محليًا فقط ونقد مرحّل >=0.01. لا يفتح البرنامج البوابات ولا يمنح الصلاحيات.

```powershell
$env:C9_JWT_ALLOW_DISPOSABLE_TEST='yes'
node scripts/test-finance-c9-jwt.cjs
```

يتحقق من حظر الأدوار الثلاثة وadmin بلا تفويض، RLS وDML المباشر والهوية المزورة، أن admin ليس مالكًا تلقائيًا، ثم طلب/اعتماد/صرف0.01 اصطناعي والاستعادة ومنع التكرار. يرفض redirects ولا يطبع التوكنات أو أجوبة Auth. لا يغني عن اختبار افتتاحي JWT على حالة خزينة فارغة مستقلة واختبار الهاتف.

## قرار المراجعة

لا يوجد قرار محاسبي متبقٍ ضمن النطاق المعتمد. يلزم المالك قبل التطبيق: مراجعة الترحيلين والتصنيفات، تشغيل PostgreSQL/COMMIT/JWT فعليًا، ثم تحديد المستخدم المالك وتفويضات الموظفين خادميًا. لا تفتح opening_enabled إلا قبل أول حركة خزينة وبعد الموافقة الصريحة. لم يبدأ C10 أو C11.
