# SYS-OFFER-LIFECYCLE-01 — دورة حياة العروض

## الوضع الحالي المثبت

- `store_offers.starts_at`: موجود، `timestamptz not null default now()`.
- `store_offers.ends_at`: موجود، `timestamptz null`.
- العروض النشطة الخمسة في البيئة البعيدة: كلها `ends_at = null`؛ لا تعدّلها المرحلة الأولى.
- القراءة الحالية تصفي البداية والنهاية، لكنها ترسل وقت الجهاز في استعلام REST.
- `add_customer_cart_offer` و`create_order_from_cart` يتحققان خادميًا من `is_active` و`starts_at` و`ends_at`، لذلك لا يمكن إتمام شراء عرض مجدول أو منتهي أو موقوف حتى لو بقي في السلة. الطلب المكتمل يحتفظ بلقطته ولا يتأثر بانتهاء لاحق.

## الترحيل المرحلي

الملف: `supabase/migrations/20261129000100_offer_lifecycle_phase1.sql`.

هو ترحيل إضافي متوافق: لا عمود جديد، لا `NOT NULL` على النهاية، لا تحديث للصفوف القديمة، ولا حذف للعقد القديم. يضيف قراءة أهلية بوقت الخادم وأقرب انتقال زمني وعقد حفظ v2 ذي فترة محددة.

ترتيب التنفيذ:

1. طبق المالك ترحيل المرحلة الأولى على Supabase وأكد نجاحه.
2. اكتمل تحديث أنواع TypeScript وتحويل واجهة التاجر والعميل إلى RPC الجديدة.
3. نجحت الفحوص البرمجية لحالات يبدأ الآن/مجدول/منتهي/موقوف والعروض القديمة؛ بقي اختبار الهاتف والسلة الفعلية من المالك.
4. بعد نشر المستهلك المتوافق فقط، ينشأ ترحيل تحصين صغير يمنع استخدام عقد الحفظ القديم للعروض الجديدة؛ لا يطبق قبله.

## الحالات المشتقة

- موقوف: `is_active = false`.
- مجدول: مفعّل ووقت الخادم قبل `starts_at`.
- نشط: مفعّل و`starts_at <= server now < ends_at`، أو عرض قديم متوافق بلا نهاية.
- منتهي: له `ends_at` ووقت الخادم وصل إليها أو تجاوزها.

لا تحتاج الحالات عمودًا متغيرًا ولا مهمة دورية؛ تشتق من الوقت والحالة المنشورة.

## المرحلة الثانية المنفذة

- محرر التاجر يعرض بداية العرض ونهايته داخل قسم واحد: «يبدأ الآن» أو موعد مستقبلي، ونهاية مطلوبة للجديد والمفعّل.
- الحفظ يستخدم `save_store_offer_v2` ويرسل `input_starts_at` و`input_ends_at` صراحةً.
- سجلات محاولات الحفظ المحلية انتقلت إلى إصدار جديد حتى لا يعاد إرسال محاولة قديمة بعقد RPC السابق.
- كتالوج العميل يقرأ المؤهل فقط من `read_customer_active_offers()`، ولا يعيد فلترة الأهلية بساعة الجهاز.
- التخزين المؤقت يحتفظ ببقية الكتالوج لكنه ينتظر قراءة الخادم قبل نشر العروض الزمنية.
- أقرب انتقال من `read_customer_next_offer_transition()` يحدد موعد إعادة القراءة؛ لا يوجد مؤقت مستقل لكل عرض.
- `OfferCard` وتفاصيل العرض تستخدمان مصدر العد المشترك نفسه، ولا يظهر عد للعروض القديمة ذات `ends_at = null` حتى يضبط التاجر نهايتها الحقيقية.

## الاعتماد النهائي

أكد المالك نجاح اختبار الهاتف واعتمد دورة الحياة كاملة ضمن `RUI-CUS-07`: البداية والنهاية، الحالات الأربع، أهلية توقيت الخادم، العد التنازلي، ومنع السلة والطلب خادميًا عند عدم الأهلية. أغلقت الصفحة، ولا يعاد تعديل هذه الدورة ضمن دفعة السلة.
