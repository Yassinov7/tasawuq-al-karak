# RUI-CUS-11 — متابعة الطلب

الحالة: **مغلقة بقبول المالك النهائي على الهاتف**. المسار الفعلي `/order-details` والملف `src/app/order-details.tsx`.

## النموذج الفعلي

السجل الرئيسي في `customer_orders`، وكل متجر يمثله `store_orders` مرتبط بـ`customer_order_id` ويحمل `store_id`. الحالات الفرعية: بانتظار المراجعة، التجهيز، جاهز للاستلام، سُلّم للسائق، مسلّم، مرفوض، وملغى. يسجل `store_order_status_history` الانتقالات وأوقاتها وملاحظة الرفض، وتشتق قاعدة البيانات حالة الطلب الرئيسي من الفروع ومهمة التوصيل. سياسات القراءة القائمة تسمح للعميل المالك بقراءة الفروع وسجلها؛ لم تتغير الصلاحيات أو الانتقالات.

## التنفيذ

- أعيد تنظيم الصفحة إلى ترويسة مشتركة، بطاقة الطلب الرئيسية، بطاقات طلبات المتاجر العمودية، ثم ملخص مالي واحد. أزيلت بطاقة المقدمة العامة، وشرائح المتاجر، وقسم المنتجات المنفصل، ومؤشر الاتصال المرئي، وتكرارات الحالة والتوصيل والإجمالي.
- أصبح تحديث الطلب إجراءً مضغوطًا في سطر عنوان «طلبات المتاجر» مع مؤشر تحميل يحافظ على البيانات المعروضة ويستدعي القراءة القائمة نفسها. نُقلت الفاتورة والإلغاء المسموح به إلى صف إجراءات داخل بطاقة الطلب الرئيسية، وحذفت مجموعة الإجراءات السفلية.
- يعرض `OrderSuborderTracking` بطاقة عمودية لكل `store_order` بشعار المتجر المنشور واسمه وحالته وعدد البنود. لا تفتح إلا بطاقة واحدة بمعرّف الفرع ويمكن إغلاقها، بينما يفتح طلب المتجر الواحد مباشرة دون أداة اختيار.
- تعرض بطاقة المتجر البنود التاريخية المجمعة وصفوف العرض والكميات والوحدات والأسعار المحفوظة وقت الطلب. لا تستخدم أسعار الكتالوج الحالية ولا تعرض صورة حالية قد توحي بأنها جزء من سجل الطلب؛ لا يتوفر snapshot تاريخي مستقل للصورة في النموذج الحالي.
- داخل البطاقة المفتوحة تظهر المراحل التي يثبتها `store_order_status_history` فقط. لا تُخترع مراحل أو أوقات مستقبلية، والرفض والإلغاء حالتان نهائيتان مع الوقت والسبب المتاحين.
- دُمجت منطقة التوصيل والعنوان والمستلم/التواصل التاريخية وحالة مهمة التوصيل الفعلية داخل بطاقة الطلب الرئيسية، وحذفت بطاقة التوصيل المستقلة. لا يقرأ عنوان العميل الحالي ولا يظهر معرّف السائق الداخلي بدل بيانات عامة غير متاحة للعميل.
- يعرض الملخص المالي الأسعار التاريخية ورسوم التوصيل والإجمالي مرة واحدة، مع تنبيه مراجعة C3 عند وجوده، ولا يضم بيانات العنوان أو إجراءات الطلب.
- تحفظ لقطة معزولة بالحساب والطلب آخر بيانات سليمة والفرع المفتوح وموضع التمرير. تحديث Realtime واحد للطلب وفروعه ومهمة توصيله يعيد القراءة دون اشتراك لكل متجر، ويحافظ على الاختيار إذا بقي الفرع موجودًا.
- بقيت البنود والعروض والأسعار التاريخية وملخص C3 والعنوان والفاتورة والإلغاء كما هي. لا Migration ولا مكتبة جديدة.

## حدود البيانات

تواريخ الانتقالات متاحة عندما يوجد سجل في `store_order_status_history`. للطلبات القديمة أو الجزئية لا تُخترع مراحل أو أوقات مفقودة؛ يعرض المكون الحالة الحالية فقط، ويستخدم وقت إنشاء الفرع لحالة «بانتظار المراجعة» الحالية. لا يوجد snapshot مستقل لاسم المتجر في `store_orders`؛ الاسم المعروض يأتي من سجل المتجر المقروء حاليًا.

## التحقق

نجح `tsc --noEmit` واختبار العقد المركز، وانتهى Expo Lint بلا أخطاء مع تحذيرين قديمين خارج النطاق في صفحتي إدارة السائقين. يغطي الاختبار البطاقات العمودية، مواضع الإجراءات الجديدة، غياب بطاقة التوصيل والإجراءات السفلية، التبديل بمعرف الفرع، البنود التاريخية، سجل المراحل وحفظ الاختيار والتمرير. لم يُشغّل محاكي أو Web أو Metro. يلزم اختبار الهاتف للتحديث والفاتورة والإلغاء، ومعلومات التوصيل، ومتجر واحد ومتاجر متعددة، وRTL والثيمين والخط المكبر.

أكد المالك نجاح اختبار الهاتف النهائي واعتمد معلومات الطلب وحالته، ودمج التوصيل التاريخي، وإجراءات الفاتورة والإلغاء، وتحديث طلبات المتاجر، والبطاقات العمودية والمتابعة الحقيقية والبنود والأسعار التاريخية والملخص المالي وحفظ الحالة والتمرير وRealtime وRTL والثيمين.
