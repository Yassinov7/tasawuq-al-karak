# Phase 10.4 — أمان Views التقييمات وتنظيف الملفات

## الإصلاح

Migration الوحيدة الجديدة: `supabase/migrations/20261018001500_review_views_invoker_security.sql`. تطبق يدويًا بعد مخطط التقييمات و004 وسياساتها، على PostgreSQL 15+. لم تُطبق على Supabase ولم تتغير migrations السابقة.

Views الأربع أُنشئت بـ `security_barrier` فقط؛ هذا الخيار لا يجعلها invoker. افتراضيًا تُفحص مصادرها بصلاحيات مالك الـView، وهو سبب تحذير Security Definer. المراجع: [PostgreSQL CREATE VIEW](https://www.postgresql.org/docs/15/sql-createview.html)، و[Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

الجداول التابعة هي `store_reviews` و`product_reviews` و`stores` و`products`. سياسات الكتالوج تعتمد أيضًا على `merchants` و`merchant_subscriptions` عبر `store_accepts_new_orders(uuid)`، وعلى `is_admin()` وملكية التاجر للمسارات المصادق عليها. دالة الأهلية القائمة SECURITY DEFINER ذات search_path فارغ، وتعيد boolean فقط، وتتحقق من قبول المتجر والتاجر وفترة الاشتراك/السماح؛ EXECUTE متاح للزائر والمصادق عليه أصلًا. لا نضيف دالة definer جديدة أو نمنح قراءة التجار/الاشتراكات للزائر.

تغيير invoker وحده غير كافٍ: جداول المراجعات بلا SELECT للأدوار العميلة، وسياساتها القديمة USING false. كذلك مسار anon في سياسات stores/products يضم subquery على merchants رغم غياب SELECT للزائر على هذا الجدول الخاص. الإصلاح:

- يضبط `security_invoker=true` و`security_barrier=true` على الأربع Views دون تغيير تعريفات أعمدتها أو استعلامات التطبيق في `src/lib/customer-reviews.ts`.
- يمنح SELECT بأسماء أعمدة التقييم العامة فقط على الجدولين، مع RLS لا يسمح إلا بالمراجعات ذات الأهلية العامة. لا SELECT شامل ولا DML مباشر. تبقى سياسة المنع القديمة للكتابة وRPCs المراجعة الذاتية والإنشاء/التعديل/الحذف كما هي.
- يحجب `customer_id` و`store_order_id` في الجدولين، وكذلك `purchased_product_id` و`store_id` الداخلي في product_reviews. لا تعرض الـViews بيانات profile أو اتصال أو أسعار الطلب. SELECT * من الجداول المصدر مرفوض؛ الأعمدة العامة المسموحة وحدها قابلة للقراءة مع ترشيح RLS.
- يجعل قراءة anon للمتاجر والمنتجات تعتمد فقط على دالة الأهلية العامة وإتاحة المنتج، مع gate restrictive. تبقى السياسات الأربع السابقة نفسها للمصادق عليهم بمسارات المالك والإدارة؛ لا تتغير صلاحياتهم الإدارية. فصل الأدوار يمنع الاعتماد على جدول التجار الخاص أثناء قراءة الزائر.
- يمنع مراجعة منتج معطل/محذوف أو منتج لا يطابق متجر المراجعة. لا تُعدّل المراجعات التاريخية؛ تبقى متاحة لصاحبها عبر RPC الذاتية وفق الضوابط القائمة.

لا يوجد حقل نشر/مسودة/إخفاء للمراجعات في المخطط الحالي؛ المراجعة تُنشأ عبر RPC لطلب مُسلّم فقط. لا نفترض وجود حالة نشر غير ممثلة. القراءة العامة الآن تتبع أهلية الكتالوج والاشتراك/السماح أيضًا؛ بعد انتهاء السماح تُحجب المراجعات العامة للمتجر، وللمنتج المعطل تُحجب مراجعاته العامة. لا تغيير لقواعد إنشاء الطلبات أو الحسابات.

`anon` و`authenticated` يقرآن التقييمات العامة نفسها، مع بقاء وصول المالك والإدارة للكتالوج وفق RLS القائمة. لا يستطيع المصادق عليه استخدام القراءة العامة للحصول على هوية كاتب آخر أو طلبه؛ استعلامات التقييمات الذاتية تستمر عبر RPC التي تتحقق من auth.uid ودور customer.

## Unrestricted

الـView لا تُفعّل عليها RLS كجدول مستقل؛ لذلك قد تبقى علامة Unrestricted في Table Editor رغم تفعيل invoker وتطبيق RLS على المصادر. إتاحة SELECT العام مقصودة للتقييمات العامة. اختفاء تحذير Security Definer وضبط الخيارات والـGRANT/RLS واختبارات allow/deny هي الأدلة المطلوبة، لا إغلاق التقييمات لإخفاء وسم الواجهة. لم نتصل بالمشروع لرؤية نص/موضع العلامة الحي؛ إن بقي تحذير أمني مختلف بعد التطبيق يلزم قراءة تفاصيله بدل افتراض أنه نفس الوسم.

## الاختبار والتطبيق اليدوي

1. راجع وطبّق Migration 015 كاملة يدويًا؛ لا حاجة لتعديل استعلامات التطبيق أو إعادة توليد types لأن أعمدة Views وRPCs لم تتغير.
2. جهّز في بيئة اختبار عبر التطبيق/RPCs مراجعات متعددة لمتجر ومنتج متاحين ضمن فترة السماح، ومراجعات أخرى لمتجر غير متاح ومنتج معطل. لا تستخدم الإنتاج لإضافة fixtures.
3. شغّل `supabase/tests/phase_10_4_review_views_security.sql` كاملًا بحساب اختبار يستطيع SET ROLE، ومع `psql -v ON_ERROR_STOP=1` إن استُخدم. ينتهي بـ ROLLBACK، ويضيف سياستين اختبار مقيدتين مؤقتًا داخل نفس المعاملة، فلا تقسّمه أو تلتزم به يدويًا.
4. يفحص invoker/barrier وRLS والأعمدة الخاصة، ثم ينتحل دور anon ودور authenticated غير مالك/مدير، ويقارن الصفوف والتعداد والمتوسطات مع المتوقع في الاتجاهين. يختبر رفض SELECT الخاص وSELECT * والكتابة المباشرة، ثم يضيف USING false restrictive ويثبت اختفاء المراجعات وصفر العدّ عبر الأربع Views؛ هذا يكشف View تتجاوز RLS. يفشل صراحة بطلب fixtures إن لم توجد بيانات موجبة/سالبة كافية، بدل نجاح صوري على جداول فارغة.
5. يدويًا جرّب العميل المسجل والزائر على صفحات المنتج والمتجر، واستمرار تعديل/حذف المراجعة الذاتية عبر RPC. أعد Security Advisor. أي grants موروثة أو سياسات إضافية غير موجودة بالمصدر تحتاج مقارنة بنتائج الاختبار الفعلية.

الفحص المحلي `node scripts/test-review-views-security.cjs` يتحقق من عقد الأعمدة المسموحة وخيارات Views وعزل سياسة anon ووجود اختبارات SQL المتراجعة. هو فحص مصدر فقط؛ لم يُنفذ PostgreSQL أو اتصال إنتاج.
