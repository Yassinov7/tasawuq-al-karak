# بنية صفحات تسوق وخطة تصميم الواجهات الكاملة — Phase 11.2

تاريخ الجرد: 2026-10-26. وثيقة تصميم وتنفيذ لاحق فقط؛ لم تتغير الشاشات أو الصلاحيات أو العمليات أو قاعدة البيانات.

## 1. حدود الجرد وطريقة قراءته

راجعت مسارات `src/app` الخمسة ذات Layout، ومداخل التنقل في الصفحات والمكونات والخدمات الخاصة بتوجيه الحساب والإشعارات. النسخ المثبتة: Expo `~57.0.27`، React Native `0.86.3`، Expo Router `~57.0.25`. هذا فحص مصدر محلي؛ الوصول المذكور مثبت في الكود، وليس ادعاء باختبار الهاتف أو توافر بيانات Supabase الحية.

يوجد **93 ملف شاشة** غير ملفات `_layout.tsx` الخمسة. `/admin/requests` يعيد تصدير شاشة `/admin/orders`، ولذلك يوجد **92 شاشة تنفيذ مختلفة**. خطوات التسجيل الثلاث شاشة واحدة، وتبويبا الكتالوج داخل شاشة واحدة، والنماذج والنوافذ ليست Routes إضافية. صفحات التاجر `products` و`offers` لها Routes فعلية لكن المستخدم يصل إلى محتواهما من الكتالوج؛ أحصيهما كملفي شاشة ولا أعدّهما رابطين رئيسيين مستقلين.

المشترك يُحسب مرة واحدة: ست صفحات مشتركة، مع ذكر الأدوار التي تستخدمها. حساب المستخدم غير المقبول ضمن الانضمام، وليس ضمن مساحة التاجر أو السائق المعتمد. `/wallet` مصنف مسارًا ماليًا قديمًا بلا مدخل مرئي، وليس ميزة محفظة زبون مقترحة.

### مفتاح مواصفات الصفحات

الجداول التالية تجمع الجرد والتصميم لكل Route: الاسم هو **عنوان AppHeader المقترح** ما لم يُذكر خلافه. «رئيسية» بلا رجوع؛ «فرعية» ترجع إلى المدخل المذكور مع fallback عند فتح رابط مباشر؛ «نموذج» يستخدم «إلغاء والعودة» مع تأكيد المسودة. عمود «التبويب» يحدد الارتباط المنطقي؛ استمرار ظهور الشريط في الفرع اقتراح فقط للتاجر والسائق، وليس وصفًا زائفًا للسلوك الحالي.

الحالات التالية عقود تصميم تُكمّلها الملاحظات الخاصة بكل صف:

- **قائمة:** تحميل أولي مكان القائمة؛ فراغ يصف غياب السجلات أو نتائج الفلتر؛ فشل مع إعادة المحاولة؛ تحديث يحتفظ بالنتائج ويُظهر أنها قيد التحديث؛ نجاح القراءة لا يحتاج نافذة.
- **تفاصيل:** تحميل الهيكل؛ عدم وجود/عدم صلاحية برسالة موحدة؛ فشل مع إعادة المحاولة؛ نجاح يعرض السجل المثبت، دون الاعتماد على منتج نشط حاليًا.
- **نموذج:** تحميل البيانات المرجعية؛ غياب الخيارات يمنع الإرسال مع السبب؛ خطأ بجانب الحقل ويحفظ المدخلات؛ إرسال مقفل؛ نجاح بعد تأكيد الخادم ثم عودة إلى المصدر وتحديثه. الفشل الملتبس لا يُصاغ «لم يحدث دفع» قبل التحقق.
- **محلي:** لا spinner لشبكة غير مستخدمة؛ غياب القيمة يعود إلى إعداد فعلي افتراضي؛ فشل الحفظ يترك الاختيار السابق؛ نجاح قصير داخل الصفحة.
- **ثابت:** لا حالات تحميل/نجاح شبكة مصطنعة؛ المحتوى قابل للتمرير وتكبير الخط؛ التعامل فقط مع تعذر فتح رابط إن وجد.

الصفوف الموسومة «تحتاج تحسين» أهداف فعلية في الخطة؛ الصفوف «موجودة» تحتفظ بتصميمها وتخضع فقط لاختبار الاتساق. رموز `S01–S14` تشير إلى مواقع Safe Area/Layout المحددة في القسم 5، ولا تعني أن التداخل شوهد على هاتف.

### وظائف لا تستدعي Routes جديدة

- اختيار الدور داخل signup يبقى خطوة؛ لا ملف اختيار دور شكلي. اختيار وحدة البيع/عملة/تصنيف بسيط يبقى selector داخل النموذج.
- إيقاف منتج، إيقاف عرض/خطة، رفض طلب بسبب قصير، إلغاء طلب، حذف عنوان/إشعار، تسجيل الخروج: تأكيدات قصيرة Modal، لا صفحات كاملة.
- الدعم الحالي للسائق إرشاد قصير؛ لا صفحة تذاكر أو محادثة دون خدمة تشغيل ودور مسؤول واضح. «عن تسوق» يعاد ربطها بالمشترك الموجود.
- إعدادات وأمان التاجر يعيدان استخدام المكونات المشتركة بالفعل؛ لا اقتراح نسخ جديدة. المسؤول يمكنه الوصول للأمان الموجود برابط من المزيد دون صفحة ناقصة إضافية.
- إدارة مناطق/تصنيفات، تعديل اعتماد السائق، رفع مستندات انضمام، دفع إلكتروني وتغيير خطة ذاتي للتاجر ليست وظائف ذات مسار إداري مخول مثبت في هذا النطاق؛ لا نصمم واجهة تنفيذ وهمية لها. الحاجة المستقبلية تُقرّر منفصلة.

## 4. خرائط التنقل وملكية Layout

### التاجر

`الرئيسية → اختصار الكتالوج/الإضافة/الطلبات`؛ `الكتالوج → منتجات \| عروض → editor`؛ `الطلبات → N03`؛ `المالية → مبيعات → تفاصيل بيع، تسويات → تفاصيل، عمولات، فواتير → N04، دفعات → N05`؛ `حسابي → شخصية، متجر، اشتراك، إعدادات، أمان، إشعارات`.

تبقى التبويبات الخمسة الحالية وثبات Header/Nav من `merchant/_layout.tsx` و`merchant-navigation.ts`، مع حفظ البحث والفلتر عبر MerchantWorkspaceContext. لا Header داخل الشاشة ولا نقل نجاح الحفظ إلى Modal. المسارات المهنية الفرعية الجديدة تُنسب لتبويبها، ولا تُضاف تبويبات سفلية. روابط القانونيات المشتركة تعود إلى موضعها ولا تتحول إلى سياق زبون.

### السائق

`الرئيسية → توفر + مهام متاحة → قبول → توصيلاتي`؛ `توصيلاتي → جارية \| سابقة → N07`؛ `حسابي → N06، حساب التوصيل → N08/N09 → N10، أمان، إعدادات، إشعارات، مساعدة، عن تسوق، خروج`.

يبقى عدد التبويبات ثلاثة. اقتراح لاحق: امتلاك `driver/_layout.tsx` Header/Nav لصفحات الدور مثل تجربة التاجر، بدل Header داخل الصفحات وBottomNav في root للمسارات الرئيسية فقط. لا نعدّل ذلك الآن. نحافظ على صفوف معلومات السائق وبطاقات المراكز حسب العملة بدل استبدالها بتصميم جديد. فصل السجلات لا يعيد حساب العهدة.

### المسؤول

`الرئيسية → يحتاج إجراء`؛ `الطلبات → تفاصيل`؛ `الانضمام → قائمة تاجر/سائق → مراجعة`؛ `المالية → مؤشرات، فواتير/دفعات/اشتراكات/ائتمان/عمولات/قيود → تفاصيل → حساب التاجر → الإجراءات`؛ `المالية → تسويات → إنشاء/تفاصيل → N17`؛ `المالية → تقارير → خمسة تقارير → المصدر`؛ `المزيد → متاجر/سائقون/خطط/عهد → تفاصيل → N18، أمان مشترك، خروج`.

**Header وBottomNav وLayout المسؤول المعتمدة تبقى كما هي.** خرائط الروابط أعلاه تنظيم محتوى. مشاكل إبراز التبويب الفرعي الحالية S13 تُسجل كقرار منفصل؛ لا تُتخذ ذريعة لتغيير الشريط. المسار `/admin/requests` ليس قسم انضمام ثانٍ. الفروع القديمة داخل index لا تصبح نظام مالية موازٍ؛ تعرض الرئيسية ملخصات وروابط إلى الصفحات القائمة.

### الزبون — ينفذ أخيرًا

`الرئيسية → متاجر → متجر → منتج/عرض`؛ `البحث → متجر/منتج`؛ `العروض → تفاصيل عرض`؛ `Header → سلة → checkout → تفاصيل طلب → فاتورة`؛ `حسابي → N11، طلبات، فواتير، عناوين → N12، مفضلة، إشعارات، إعدادات/أمان`؛ `ملخص التقييم → N13 → N14 للمؤهل`.

تبقى التبويبات الأربعة الحالية. في التصميم المقترح تظهر فقط على الصفحات الأربع الرئيسية، وتُعامل التفاصيل/السلة/checkout كمهمة فرعية ذات رجوع واضح، دون شريط سفلي منافس لزر الشراء. العودة تحفظ نتائج البحث وتصنيف المتجر. لا ربط `/wallet` للزبون قبل قرار صلاحية هذه الميزة القديمة.

### غير المسجل والانضمام

`/ → login ↔ signup (تعريف → بيانات → دور وشروط) → verify-email إن لزم → login → توجيه حسب الدور`؛ الزبون إلى home؛ التاجر/السائق بلا طلب إلى نموذج انضمامه؛ الطلب غير المقبول إلى application-status؛ المقبول إلى مساحة الدور؛ المسؤول إلى admin. `login → طلب رسالة استعادة → N02 من رابط بريد صالح → login`.

لا BottomNav في المصادقة أو الانضمام أو مراجعة الطلب. لا افتراض أن «إلغاء» يعيد المنضم إلى متجر لم يُنشأ. fallback يمر عبر توجيه الحساب أو خيار واضح للعودة إلى الدخول/الخروج، دون حلقة تعيد فتح النموذج آليًا.

## 5. Safe Area وLayout — 14 موقع معالجة محددًا

### القاعدة المشتركة المقترحة

مالك واحد لكل حافة: Layout يحجز Header + top inset، والصفحة لا تضيف top ثانية. حيث لا Header مشترك، SafeArea على غلاف الصفحة نفسه. إذا Nav موجود، Layout يحجز ارتفاعه الفعلي مع bottom inset مرة واحدة؛ وإذا لا Nav، الصفحة تحجز inset أسفل آخر إجراء. الفاصل الجمالي مستقل عن مساحة النظام. لا يكفي `Spacing.ten` كبديل لـinsets.

الزر السفلي الثابت له ارتفاع مقاس، ويُضاف نظيره إلى padding قائمة المحتوى؛ النموذج الطويل يتمرر مع لوحة المفاتيح، ويظل الحقل الأخير والخطأ وزر الإلغاء قابلين للوصول. offset يتبع Header الذي يقع خارج KeyboardAvoidingView، دون تخمين رقم ثابت أو إضافة inset مرتين. التأكيد القصير يحد ارتفاعه بالمساحة الآمنة ويتيح تمرير محتواه عند الخط الكبير؛ الخلفية لا تغلق أثناء إرسال. لا نفترض وجود مكتبة BottomSheet؛ الموجود `AppModal` وModal العنوان. الحد الأدنى للمس 44 تقريبًا والصفوف ملتفة في RTL، دون قطع مرجع أو مبلغ طويل.

## 6. تدفق طلب انضمام التاجر — التصميم المطلوب دون تغيير السلوك الآن

### السلوك الحالي المثبت

`src/app/merchant-application.tsx` يحفظ مسودة محلية مرتبطة بمعرف المستخدم، ويحمل الخطط والتصنيفات النشطة، ويستدعي `submit_merchant_application` مباشرة من submit، ثم يمسح المسودة وينتقل إلى application-status. زر Header اسمه «رجوع» وينفذ `router.back()` دون قرار مسودة. لا توجد مرفقات أو رفع وثائق في الحقول/RPC الحالية؛ لا نرسم قسم ملفات وهميًا.

### التدفق المقترح

1. Header «إنشاء متجر» وإجراء صريح **«إلغاء والعودة»** بدل سهم غامض. قبل أي تحرير، الخروج إلى أصل آمن معلوم. بعد تعديل أي قيمة مقارنة بالمسودة عند الدخول، اعرض تأكيدًا بثلاثة قرارات واضحة: **«حفظ المسودة والعودة»**، **«تجاهل التغييرات والعودة»**، **«متابعة التعبئة»**. حفظ draft لا يعني إرسال الطلب. تجاهل التغييرات يعيد المسودة عند الدخول؛ وإن لم توجد مسودة أصلية يحذف المسودة الجديدة لهذا المستخدم فقط.
2. زر Android hardware back وأي gesture مغادرة للشاشة يتبعان القرار نفسه. من شاشة المراجعة، back/«العودة للتعديل» يعودان للنموذج بالقيم نفسها دون حذف؛ خروج التدفق كله يمر بقرار المسودة. أثناء الإرسال الفعلي تُمنع إعادة الضغط أو مغادرة ملتبسة، ويُعرض «جارٍ تقديم الطلب».
3. زر النموذج «تقديم الطلب» يتحقق محليًا ثم يفتح N01 **دون أي RPC كتابة**. تمرير المسودة يكون عبر مخزن مرتبط بالمستخدم/معرف مسودة، لا الهاتف والعنوان والوصف داخل URL.
4. شاشة «مراجعة طلب المتجر» قراءة فقط: هوية المتقدم المتاحة من الجلسة، اسم المتجر، الوصف أو «لم يضف وصفًا»، اسم التصنيف، الهاتف، العنوان، الخطة باسمها ومدتها ورسمها وعملتها وعمولتها وحد المنتجات وميزاتها الفعلية. تمييز اختيار الخطة عن اشتراك بدأ بالفعل. المرفقات لا تظهر لعدم وجودها؛ إذا أضيفت مستقبلًا بعقد بيانات مستقل تعرض الملفات الفعلية فقط.
5. إجراءان: **«العودة للتعديل»** و**«تأكيد تقديم الطلب»**. قبل التأكيد تُعاد صلاحية الخطة/التصنيف من المصدر، دون إعادة تعيين اختيار المستخدم بصمت. تغيّر شروط الخطة يوقف التأكيد ويطلب مراجعة الاختيار الجديد. فتح المراجعة بلا مسودة أو بحساب آخر يعيد للنموذج برسالة، ولا يستعمل آخر مسودة مستخدم سابق.
6. عند التأكيد فقط يُستدعى **RPC الحالي وبنفس توقيعه وقواعده**. قفل إرسال واحد للتدفق، والتحقق من وجود الطلب إذا كانت النتيجة ملتبسة قبل إعادة الإرسال. النجاح المؤكد يمسح المسودة ثم يوجّه للحالة؛ الفشل يبقيها ويتيح التعديل وإعادة المحاولة. لا طلب وهمي عند فتح الشاشة أو العودة إليها.

### الملفات المقصودة في مرحلة التنفيذ اللاحقة

- تعديل `src/app/merchant-application.tsx` لزر الإلغاء والتحقق ثم الانتقال فقط، مع إبقاء النموذج والحقول الحالية.
- إنشاء `src/app/merchant-application-review.tsx` لشاشة N01.
- استخراج الجزء المشترك من المسودة/التحقق/الإرسال إلى ملف واحد صغير خارج Routes، مثل `src/lib/merchant-application-draft.ts`، بعد فحص إمكانية إعادة استخدام local-cache الحالي؛ لا نسخ منطق submit إلى شاشتين.
- إعادة استخدام `src/components/ui/AppModal.tsx` للتأكيد القصير بعد تحسين الحواف؛ عند الحاجة غلاف انضمام صغير في `src/components/auth/` بدل تكرار Header/SafeArea. إعادة استخدام الموجود أولًا.
- `src/app/application-status.tsx` فقط إذا لزم fallback وحفظ استكمال الطلب؛ لا تعديل RPC أو migration أو شروط قبول الإدارة.
- التسجيل واختيار الدور وتهيئة المتجر بعد الموافقة تبقى بمساراتها وقواعدها الحالية؛ لا «إنشاء متجر» ثانٍ عند تأكيد نموذج الانضمام.

هذه أسماء تنفيذ مقترحة، **لم تُنشأ الملفات ولم يُنقل استدعاء RPC الآن**.

## 7. النوافذ والتكرار والبيانات غير المكتملة

### حصر النوافذ حسب الوظيفة

- **AppModal المشترك:** استعادة البريد في الدخول، حالة إعادة إرسال التحقق، حذف إشعارات، حذف سلة/عرض/عنصر، تأكيد checkout وإلغاء طلب، تنبيهات أمن وتفضيلات. هذه قرارات قصيرة تبقى نوافذ؛ رسالة نجاح عادية يفضل أن تكون inline إن لا تتطلب قرارًا.
- **التاجر:** products/offers تأكيد إيقاف وتنبيه؛ orders نافذة سبب الاعتذار وfeedback؛ account خروج؛ الأمان نجاح. تبقى قصيرة. تفاصيل طلب التاجر حاليًا محتوى بطاقة طويل وليست Modal، لذا N03 فصل محتوى وليس تحويل نافذة.
- **السائق:** خروج ودعم/عن التطبيق في account؛ الإجراءات التشغيلية داخل بطاقات DeliveryTaskCard وليست صفحة تفاصيل أو BottomSheet. الدعم القصير يبقى، «عن تسوق» يعاد استخدام صفحته القائمة.
- **المسؤول:** قرار انضمام مع ملاحظة قصيرة يبقى؛ merchant-finance يحتوي payment/credit/plan/renew/autoRenew/reconcile/reverse في ActionModal؛ الدفع ذو التخصيصات والائتمان فقط يتحولان M1/M2. دفعة التسوية M3، استلام/صرف عهد السائق عائلة واحدة M4. تغيير الخطة/تجديد/عكس قصير يبقى تأكيدًا مع تمرير آمن؛ لو تطاول المحتوى على الهاتف يُراجع في مرحلته ولا نضيف صفحات احتياطية الآن.
- **Modal خاص:** حذف العنوان في addresses؛ يبقى تأكيدًا ويأخذ قاعدة S10. نموذج العنوان نفسه مضمّن وليس Modal.
- لا يوجد مكون BottomSheet مستقل في التدفق الذي راجعته؛ لا إدخال مكتبة له. محدد الوحدة والاختيارات inline ليست نوافذ تُحصى في التحويل.

### قرارات تبسيط دون حذف الآن

- index المسؤول يحتفظ بفروع مراجعة طلبات/سائقين/متاجر/محافظ/خطط مع صفحات مستقلة فعلًا. التنقل الحالي غالبًا ينتقل للصفحة المتخصصة؛ الوثيقة لا تحسب تلك الفروع Routes جديدة ولا تنصح بإحياء مالية المحفظة القديمة. في التنفيذ المحتوى المختصر يحيل إلى المصدر الموجود، وأي إزالة كود تحتاج مراجعة استخدام منفصلة.
- `/admin/requests` alias للطلبات؛ توحيد الروابط لا يتطلب إنشاء شاشة أو تغيير دورة الطلب. `/merchant/products` و`offers` تبقى Routes توافق ومصدر panels؛ لا تحذف ملفات Routes بسبب عدم ظهور زر لها.
- ملف معلومات السائق المستقل **مفقود** رغم وجود المعلومات نفسها في account؛ التصميم الجيد الموجود يُنقل دون إهدار.
- هوية الزبون تقرأ cache وتعود مبكرًا في home/account؛ تحتاج تحديثًا عند العودة، لا عرض بيانات قديمة كأنها أحدث نسخة. بيانات التاجر بالفعل تُحمّل عند focus، فلا نضيف query مكررًا.
- driver/cash-account يجلب المراكز والسجلات دفعة واحدة ويحمّل عند mount مع refresh يدوي؛ التقسيم والعودة يحتاجان تحديثًا موجّهًا وpagination بدل نسخ رصيد محسوب محليًا.
- فواتير ومدفوعات اشتراك التاجر تملك قوائم، لكن ليس تفاصيل تخصيص مماثلة للإدارة. N04/N05 لا يجوز بناؤهما على بيانات RPC إداري أو افتراض سماح تغيير merchantId.
- عمليات الدفع المالي يجب أن تقول «تعذر تأكيد النتيجة، حدّث السجل» عند timeout. توجد حاليًا صياغة قطعية في دفعة تسوية المسؤول؛ إصلاح النص/حالة النتيجة جزء من تصميم العملية، لا إثبات ثغرة محاسبية أو تغيير قواعد خادم.
- عملة/مبالغ وصورة المنتج الحالي لا تستبدل snapshots في طلبات قديمة؛ الحالات الملغاة/المرفوضة/المسلّمة تُعرض بأسمائها ولا تُختصر إلى نجاح عام.

## 8. خطة التنفيذ اللاحقة بالترتيب الملزم

### المرحلة 1 — الانضمام وSafe Area والقواعد المشتركة

إنشاء N01 وN02؛ تحسين merchant-application وdriver-application وapplication-status وlogin/signup/verify-email حسب القسم 2. ضبط S01/S02/S03/S10 وقواعد ownership للحواف والرجوع والمسودة؛ لا تعديل Layout المسؤول. نوافذ استعادة البريد والتأكيد القصير تبقى Modal؛ لا تحويل من M1–M4 بعد.

**اكتمال على الهاتف:** تعبئة متجر ثم خروج بحفظ/تجاهل/متابعة، Android back والgesture متطابقان، رجوع من المراجعة لا يمحو حرفًا، لا RPC عند الانتقال للمراجعة، ضغطة تأكيد واحدة ترسل مرة، انقطاع يحتفظ بالمسودة، تبديل حساب لا يظهر مسودته؛ بريد طويل وشاشة صغيرة ولوحة مفاتيح لا تحجب إجراء؛ recovery صالح/منتهي يُوجّه بصورة مفهومة. يلزم تحقق تشغيلي من روابط Auth دون تغيير خطة العمل.

### المرحلة 2 — إكمال التاجر

إنشاء N03 وN04 بعد اعتماد مصدر التفاصيل؛ N05 تحسين لاحق إن لم يتوفر مصدر آمن. تحسين editors والطلبات وقوائم الفواتير/الدفعات؛ الإبقاء على حسابي والاشتراك والمالية والكتالوج والأساس الجيد في 11.1. لا Modals تتحول هنا: رفض الطلب وإيقاف المنتج/العرض تأكيدات قصيرة. Layout ثابت بالفعل؛ تضاف mappings للفروع الجديدة فقط، مع مصدر الدور للمشترك S06.

**اكتمال على الهاتف:** كل فرع يعرض عنوانًا ورجوعًا وتبويبه الصحيح، فلاتر الكتالوج لا تضيع، آخر حقل وزر حفظ فوق الكيبورد، منتج موقوف ظاهر للتاجر وغير قابل للبيع، تفاصيل طلب قديم تعمل دون منتج نشط، الفاتورة والدفعة لا تتبادلان نوعهما، ماليات كل عملة منفصلة، العودة تحدّث الشاشة دون تحميل مكرر غير ضروري. لا زر تغيير خطة ذاتي غير مخول.

### المرحلة 3 — إكمال السائق

إنشاء N06/N07/N08/N09؛ N10 لاحق إن لزم تفصيل إيصال. تحسين الأربع الحالية؛ نقل معلومات account كما هي بصريًا، وتفكيك حساب التوصيل مع إبقاء بطاقات المراكز. توحيد ملكية Header/Nav في driver layout فقط ومعالجة S04/S05/S06. لا Modal تفاصيل مهمة حاليًا لتحويله؛ فصل بطاقة طويلة، ودعم/خروج قصيران.

**اكتمال على الهاتف:** اعتماد السائق ظاهر، الرجوع من الأمان والسجل لا يفتح حساب الزبون، المهام الجارية والسابقة منفصلتان، التفاصيل المحمية لا تظهر قبل الإسناد، تعارض قبول مهمة يعطي تحديثًا مفهومًا، تغير الحالة يحدّث إجراء التفاصيل، استلام المكتب/صرفه قراءة فقط للسائق، نهاية السجل وأزرار الحالة لا تتداخل مع Nav أو الإيماءات. لا تغيير تسلسل الاستلام/التسليم.

### المرحلة 4 — تنظيم محتوى المسؤول والمالية

إنشاء N15/N17/N18؛ N16 لاحق إن رغبت الإدارة بفصل الائتمان. تحويل M1/M3/M4 أولًا وM2 عند N16. تحسين الرئيسية/finance/merchant-finance/create-settlement/settlement-details/custody-details/plan-form ومحتوى more؛ ربط الأمان المشترك. الإبقاء على **Admin Layout وHeader وBottomNav بالكامل**؛ S13 مسألة مطابقة فرع تحتاج إذنًا مستقلًا، ويمكن تركها دون تعطيل بقية المرحلة.

**اكتمال على الهاتف:** إنشاء تسوية بلا مستحقات يعرض فراغًا لا spinner، العملة والتاجر لا يتغيران صامتًا، مراجعة دفعة جزئية وتخصيصها قابلة للقراءة بيد واحدة، timeout يعرض نتيجة غير محسومة مع رابط السجل، لا ضغط مزدوج، رصيد السائق المتاح والعملة ظاهران قبل تأكيد المكتب، التقارير تفتح المصدر وتحتفظ بفلاترها، Header/Nav المعتمدان لم يتغيرا. الاختبار يؤكد القواعد الخادمية الحالية ولا يعيد كتابتها.

### المرحلة 5 — الزبون أخيرًا

إنشاء N11/N12؛ N13/N14 تحسين لاحق، مع بقاء ratings المضمّن حتى اكتمال نقله. تحسين الصفحات الموسومة في جدول الزبون، وخاصة checkout والمزامنة وبيانات الملف؛ لا إعادة بناء البطاقات العامة. نموذج العنوان/التقييم فصل من محتوى وليس تحويل Modal؛ تأكيدات السلة والحذف والإلغاء وcheckout تبقى. معالجة S07/S08/S09/S14 مع إبقاء التبويبات الأربعة.

**اكتمال على الهاتف:** البحث والعودة يحفظان الاستعلام/الموضع، عرض قديم بمنتج معطل لا يُشترى، السلة تعرض سبب المنع وإزالته، تحديد عنوان من محرره يعود إلى checkout، أرقام العملتين لا تجمع، طلب متعدد متاجر يشرح الرفض/الإلغاء الجزئي، فاتورة snapshot تبقى مقروءة، التقييم لا يقبل غير مؤهل، تحديث الهوية يعكس المصدر بعد العودة.

### المرحلة 6 — اختبار الاتساق عبر الأدوار

لا صفحات جديدة ولا تحويلات. اختبار مصفوفة role × دخول طبيعي/رابط مباشر/إشعار × session صالح/منتهٍ × تحميل/فراغ/خطأ/سجل محذوف أو غير مخول. مراجعة Safe Area بوضع الإيماءات والأزرار الثلاثة وiOS ذي النتوء وشاشة صغيرة وخط كبير وRTL، ولوحة المفاتيح في آخر حقل، ونهاية كل قائمة طويلة. التحقق من إغلاق Modal بالرجوع وعدم إغلاقه أثناء تنفيذ، ومن fallback بلا history ودون حلقات.

**اكتمال:** لا Header مزدوج، لا إجراء تحت Nav، لا انتقال لسياق زبون من دور مهني، كل رابط تفاصيل صالح/غير صالح له نتيجة واضحة، لا طلب كتابة من شاشة قراءة/مراجعة قبل التأكيد، TypeScript/Lint والفحوص المحلية المناسبة تمر بعد التنفيذ. عدم تشغيل Metro/Web في مرحلة التخطيط الحالية؛ هذه معايير للمرحلة اللاحقة على الهاتف.

أماكن التكرار المثبتة التي تُرحّل عند العمل عليها: scrim في `AppModal.tsx` و`addresses.tsx`، خلفيات الوسائط وأيقونات الأبيض في `ProductMediaPreview.tsx`، الأبيض في `merchant/offers.tsx` و`merchant/product-editor.tsx`. تستبدل بـoverlay/onMedia/onPrimary بحسب الخلفية الفعلية، لا استبدال آلي لكل أبيض. ألوان الرسم في `SyriaFlag.tsx` ألوان أصل ثابت؛ ليست tokens لحالات التطبيق ولا تُلوّن وفق Theme. لون الظل في Shadows يبقى مركزيًا.

### 10.3 Typography — تخفيف محدود مع وضوح العربية

السلم الحالي: xs=12، sm=14، md=16، lg=18، xl=22، xxl=28، display=34. لا تصغير شامل: 12 يبقى حدًا للتفصيل غير الأساسي فقط، و14 حد عملي للنص المعتاد والحقول المالية. تعتمد المقاييس الجديدة على الغرض بدل تعديل كل استخدام lg/xxl دفعة واحدة.

|---|---|---|
| `caption` | 12 / 20 / Regular أو Medium | توقيت أو معرف ثانوي؛ ليس مبلغًا لازمًا أو خطأ نموذج صغيرًا يصعب قراءته |

لا تعطيل لتكبير الخط ولا حصر لسطر اسم/عنوان/خطأ في ارتفاع ثابت. المقاييس بوحدات التخطيط المعتادة الحالية؛ الارتفاعات الدنيا تنمو مع النص. تختبر Cairo مع التشكيل والنص الطويل والأرقام العربية/اللاتينية؛ المبلغ والعملة لا ينفصلان بشكل ملتبس، والمعرف الطويل يلتف أو يُنسخ من التفاصيل. لا تحويل الأرقام إلى صور ولا قص المبلغ بعلامة حذف. لا تقليل lineHeight بغرض احتواء بيانات أكثر.

### 10.4 Spacing وكثافة البيانات

السلم الحالي مناسب كأساس: 2، 4، 8، 12، 16، 20، 24، 32، 40، 48، 64. المشكلة في التركيب: `AppTextField` يجمع marginTop=12 وgap=8 مع gaps الحاوية، وAccountSection يضيف marginTop=16 فوق gap الصفحة، وبعض صفحات الإدارة تضيف padding=20 وgap=12 داخل سلسلة بطاقات. بطاقة التاجر المالية الحالية أقرب للهدف: padding=16 وgap=8، فلا تُضغط بلا داعٍ.

| Token مقترح | القيمة | مجال التطبيق |
|---|---:|---|
| `pageGutter` | 16 | بدل 20 في محتوى الصفحات الكثيف عند مراجعته، مع عرض أقصى حالي؛ لا تغيير Header/Nav |
| `sectionGap` / `cardGap` | 16 / 12 | فصل مجموعات المعنى، وليس هوامش متراكمة بين كل عنوان وبطاقة |

في المالية: بطاقة صف مختصرة تضع رقم المستند والحالة أولًا، المبلغ والعملة ثانيًا، وتاريخًا ومرجعًا ثانويًا؛ التفاصيل والملاحظات والتخصيصات في صفحتها. حقول التسمية/القيمة بعمودين مرنين، وتتحول إلى تكديس عند ضيق العرض أو تكبير الخط. لا جدول أفقي لإتمام الدفع أو فهم المتبقي. تعرض المجاميع مرة واحدة لكل عملة؛ تقليل تكرار العناوين وUUID والأزرار الكبيرة المتطابقة أهم من تصغير الخط. الحفاظ على البيانات والحسابات وحقول snapshot كاملة، مع إتاحتها بالتفاصيل لا حذفها.

المسافات 40/48/64 لا تستخدم أسفل كل بطاقة كزخرفة؛ تبقى عند وجود سبب، ومنها فراغ تنفس أو إجراء ثابت. مساحة Safe Area واحتياطي Nav/footer ليست Spacing قابلة للتقليل؛ تظل وفق قواعد القسم 5 وارتفاع المكون الفعلي.

### 10.6 التباين والتحقق في Light/Dark

حساب محلي للألوان الصلبة الحالية بطريقة luminance النسبية أعطى: textMuted الفاتح على الأبيض **2.93:1** وعلى background **2.83:1**؛ textSecondary على الأبيض **5.12:1**. الأبيض على accent الفاتح **2.56:1** بينما accentText الداكن عليه **6.10:1**؛ لذا يظل الذهب خلفية مع نص داكن أو زخرفة، وليس نصًا صغيرًا فوق الأبيض. onPrimary الداكن المقترح فوق primary في Dark يقارب **6.78:1**. هذه قياسات أزواج محددة، وليست نتائج اختبار كل شاشة.

هدف القبول للنصوص العادية والمساعدة المقروءة **4.5:1**، ولحدود/أيقونات التحكم الضرورية **3:1** مع السطح المجاور؛ حتى عند كفاية تباين عنوان كبير يُفضّل عدم تخفيض وضوح نص مالي. الفاصل الزخرفي الخفيف ليس حد حقل وحيدًا يعتمد عليه المستخدم. تُقاس حالات pressed/selected/focus أيضًا، وتُركّب شفافية overlay على الخلفية الفعلية قبل تقييم النص. لا افتراض أن نفس شفافية الضوء مناسبة لـDark. المحتوى المعطل يحتفظ بوضوح عملي ولا يُستخدم انخفاض تباينه لإخفاء سبب المنع.

معيار الهاتف: التبديل Light/Dark/System، تكبير الخط، حقل مركز/خاطئ/قراءة فقط/معطل، زر عادي/ضغط/تحميل/تعطيل، بطاقة نجاح/تحذير/رفض/معلومات، Modal وعارض وسائط، وماليات طويلة متعددة العملات. القياس المحلي للألوان يُستكمل بفحص العربية على الهاتف؛ لا ادعاء قبول بصري قبل ذلك.

### 10.7 التطبيق التدريجي قبل وأثناء Phase 11.3

1. في المرحلة المشتركة الأولى: اعتماد الأسماء والأزواج في `theme.ts` مع بقاء aliases القديمة، وإضافة مقاييس typography/spacing/controls دلالية في المصدر نفسه عند التنفيذ؛ لا Theme ثانية ولا تغيير شامل للسلم الحالي. فحص أزواج الألوان آليًا محليًا مناسب حين تُعتمد القيم، دون قاعدة بيانات.
2. ترحيل AppButton/AppTextField/AppModal/AppIcon بحذر: للمكونات واسعة الاستخدام تُضاف variant أو مقاييس اختيارية وتبدأ في صفحات الانضمام التي نعمل عليها؛ لا تعديل default يؤثر على شاشات سليمة أو chrome المسؤول بلا مراجعة. لا حاجة لبناء مكتبة مكونات كبيرة.
3. التاجر ثم السائق: تطبيق المقاييس على المحتوى المعدّل فقط، وإعادة استخدام AccountShell/AccountSection/البطاقات المالية. مراجعة composed spacing بدل خفض كل padding. الحفاظ على وحدة Cairo وRTL ونجاح الحفظ الواضح.
4. المسؤول: توحيد badges والمبالغ والفلاتر والصفوف داخل المحتوى المالي؛ **Header وBottomNav وأبعادهما وألوانهما المعتمدة وسلوك التنقل خارج نطاق التغيير**. أي token مشترك قد يؤثر عليهما يُعزل باختيار المكون/variant قبل اعتماده عالميًا.
5. الزبون أخيرًا وفق الخطة الأصلية؛ لا إعادة تصميم الكتالوج أو الصفحات السليمة لمجرد وجود token جديد. في كل ملف نلمسه، تُزال الألوان الخام المتعلقة بالواجهة فقط، مع إبقاء ألوان الأصول الثابتة.
6. قبول كل دفعة: لا قص عربية أو مبالغ، مساحة لمس مناسبة رغم الكثافة، تباين الزوجين الفاتح/الداكن وحالاتهما، لا regression في Admin chrome، لا تغير business/RPC/DB، وفحوص TypeScript/Lint/whitespace. هذا القسم لا يغيّر أعداد الصفحات أو أولويات تنفيذ الأدوار في الملخص التالي.
