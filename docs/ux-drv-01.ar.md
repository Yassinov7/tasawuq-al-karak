# UX-DRV-01 — بطاقات مهام السائق والمراجع والمنتجات

الحالة: **معتمدة ومغلقة وفق قبول المالك الصريح عند بدء UX-CARDS-03**. هذه متابعة محددة بطلب المالك لـRUI-DRV-02 `/driver/orders` وRUI-DRV-02.01 `/driver/task-details` معًا، لا إعادة فتح بقية صفحات السائق. تقرير `arabic-ux-review.ar.md` ونمط A هما مرجع البداية. لا تغيير لتنفيذها ضمن UX-CARDS-03.

## الفجوة المثبتة والتنفيذ

كانت بطاقة القائمة تُرسم مباشرة في `orders.tsx`، بينما `DeliveryTaskCard` القديمة بلا مستهلك فعلي. احتوت القائمة وجهة مفصلة ومستلمًا ومعاينة نقاط الاستلام، ولم تقرأ الخدمة بنود المنتجات ولا تمرر ORD وSOR من سياق C3 رغم توفرها.

أعيد تصميم `DeliveryTaskCard` وربطها فعليًا داخل `orders.tsx`. البطاقة بإطار واحد ومسافات مدمجة: عنوان «مهمة توصيل» وTSK بارز، شارة حالة عربية واحدة، ORD، ملخص المتاجر والأصناف والكميات، المنطقة، ومبلغ التحصيل المعتمد للمهمة الجارية عند تحقق القراءة. السطر الأخير إجراء واحد يفتح التفاصيل بحسب المرحلة: عرض نقاط الاستلام أو مراجعة التسليم والتحصيل. لا تنفيذ استلام أو تسليم من بطاقة القائمة.

لا عنوان تفصيلي أو اسم مستلم أو أسماء منتجات في القائمة. ارتفاع البطاقة مرن، والترويسة تلتف عند العرض الضيق أو تكبير الخط. تستخدم مساعدات RTL ورموز الثيمين، مع إبقاء اتجاه المراجع اللاتينية دون قلب الحاويات.

## القراءة والصلاحيات

- المصدر `getDriverAssignedTasks` في `driver-deliveries.ts`؛ شرط `driver_id` والتحقق من الحساب قبل وبعد القراءة وإلغاء الطلبات موجودة ومحفوظة.
- المراجع من `get_c3_order_context` وعقده الحالي: `TSK:task.id` و`ORD:customer_order_id` و`SOR:store_order.id`. لا تخمين مرجع من UUID أو رقم الطلب، ولا روابط لصفحات عميل لا يملكها السائق. عند غياب المرجع يعرض نص صريح.
- بنود `store_order_items` تقرأ بأسماء ووحدات وكميات الشراء التاريخية: `product_title_snapshot` و`selling_unit_snapshot` و`quantity`. يبقى المنتج المحذوف ظاهرًا حتى لو كان `product_id` فارغًا. لا استعلام إلى كتالوج المنتجات الحالي.
- قراءة البنود مجمعة على متاجر الدفعة، لا طلب لكل منتج: 80 معرف متجر كحد لكل نطاق، و100 بند كحد لكل استجابة، ومؤشر `id` ثابت حتى استجابة فارغة. تستكمل الصفحات القصيرة أيضًا لتجنب اعتبار سقف استجابة الخادم نهاية للنتائج. لا تسحب بنود المهام الأخرى أو الأسعار.
- سياسة `store_order_items_read_participants` تستعمل `can_view_store_order`؛ الدالة القائمة تجيز السائق المسند إلى الطلب الرئيسي. تمت مراجعة مصدر الترحيلات المحلية، دون ادعاء فحص قاعدة المالك الحية. لا RPC جديدة أو تغيير RLS أو Migration مطلوبة.
- قراءة المهام المتاحة بقيت منفصلة عبر `list_available_delivery_tasks`، دون جلب بنود أو معلومات عميل قبل الإسناد. لم تُعد تصميم الرئيسية `/driver` ضمن هذه الدفعة؛ بطاقاتها المتاحة تحافظ على الحقول العامة المسموحة.
- فشل قراءة البنود لا يخفي المهمة أو التحصيل ولا يعرض صفرًا كأنه قراءة ناجحة؛ حالة `productsState=unavailable` تعرض تعذر القراءة، وفي التفاصيل إعادة المحاولة عبر التحديث القائم. لا تنشر نتائج جزئية للبنود إذا فشلت صفحة منها.

## التفاصيل والاستلام الجزئي

بقي ملخص المهمة والمبلغ ووجهة التسليم والتعليمات والاتصال وإجراءات التسليم والتحقق من محاولة سابقة كما هي وظيفيًا. قسم «الطلبات والمنتجات» يجمع ORD ثم المتاجر المطلوبة، مع SOR واسم المتجر ونقطة الاستلام وحالته وبنوده وكمياته وملاحظته المحفوظة. لا تكرر مجموعة المنتجات في قسم آخر.

استُخدم `StorePickupPanel` الحالي مع `renderContents` اختياري لعرض `DriverStoreContents` تحت المتجر نفسه. الاستلام الجزئي من `workflow.confirmed`، وعدّاد الاستلام لا يعني اكتمال المهمة قبل جميع المتاجر. شروط الزر والقفل و`canConfirmPickup` والتحقق الخادمي لم تتغير. عند غياب workflow تظهر التفاصيل المحفوظة بلا إنشاء زر استلام بديل؛ المهمة المكتملة تعرض بنودها ولا تعرض إجراء تحصيل جديد.

عدد الأصناف يعتمد هويات المنتجات المحفوظة، ومع فقد هوية المنتج لا يخمن دمجه مع منتج آخر من الاسم. الكميات تجمع بدقة عقدها ذي ثلاث منازل بحسب وحدة البيع؛ مثال القطع والكيلوغرامات يبقى مجموعين منفصلين، لا رقم «وحدات» مضللًا. المتاجر الملغاة أو المعتذرة تستبعد من ملخص حمولة التوصيل ومن عمليات الاستلام وفق السلوك القائم.

الملاحظات الموجودة في العقد هي ملاحظة طلب المتجر وملاحظة العميل العامة؛ الأخيرة باقية في وجهة التسليم للمهمة المسندة الجارية والمتحقق منها. لا يوجد حقل مستقل لملاحظة كل منتج في عقد البنود، ولم تختلق الواجهة واحدًا.

## ما لم يتغير

ترقيم القائمة بعشر مهام، البحث الخادمي TSK، ترتيب المهام، مفاتيحها، حفظ الحالة والعودة وآلية التركيز وRealtime وعزل الحساب باقية. لم تتغير دوال القبول والاستلام والتسليم والتحصيل أو أسعار C3 أو الإشعارات أو Cron أو الصفحات المالية. لا مكتبة أو بناء أو نشر أو إجراء بعيد. لا بيانات تحتاج انتظار ترحيل جديد.

- `node scripts/test-driver-task-ux.cjs`: ست مجموعات ناجحة للقراءة والمراجع والبنود التاريخية والكمية، وسقف استجابة اصطناعي ببند واحد، والفشل الجزئي والبيانات الأجنبية والإلغاء وتبديل الحساب، وبطاقة القائمة ومحتوى المتجر والاستلام الجزئي في اتجاهي النظام.
- `node scripts/test-driver-refresh.cjs`: ناجح؛ فحص المكونات الفعلية للقائمة والتفاصيل، الترقيم والبحث، التركيز والخلفية والردود القديمة، سحب الإسناد، خصوصية الوجهة، وقفل الاستلام والتسليم. حُدّث توقع القائمة لحجز بيانات المستلم للتفاصيل.

- TypeScript وLint للملفات المتأثرة: ناجحان، بتشغيل واحد لكل منهما. فحص فرق الملفات بلا أخطاء تنسيق.

هذه مهايئات محلية للكود الفعلي، لا اختبار هاتف أو SQL حي أو إثبات تطبيق RLS بعيد. لم يشغّل Expo أو Metro أو متصفح أو محاكي أو APK.

## اختبار الهاتف

1. مهمة مسندة بمتجر واحد ثم عدة متاجر: مطابقة TSK وORD وSOR مع سجلاتها، وملخص الكميات مع البنود. فتح المهمة والرجوع إلى البحث/الصفحة نفسها.
2. منتجات بقطع وكميات كسرية ووحدات مختلفة، ومنتج قديم/محذوف: عرض الاسم والوحدة التاريخيين وبقاء جميع البنود، دون جمع وحدات غير متجانسة.
3. استلام متجر واحد فقط: يظل الآخر بانتظار الاستلام، ولا يتاح التسليم النهائي قبل استكمال المتاجر وشروط الخادم. بعد الاستلام الكامل جرب التسليم والتحصيل المعتمدين.
4. مهمة متاحة غير مسندة: لا بيانات عميل أو بنود خاصة. تبديل حساب السائق أو سحب الإسناد أثناء القراءة: لا بقاء بيانات غير مصرح بها.
5. انقطاع الشبكة والعودة والتحديث؛ فشل قراءة البنود لا يعني سلة منتجات فارغة ولا يغيّر مبلغ التحصيل. مهمة مكتملة لا تعرض طلب قبض جديدًا.
6. فاتح/داكن، 320 و360، أسماء ومراجع طويلة وخط مكبر؛ التأكد من التفاف الترويسة ووضوح زر فتح التفاصيل والتمرير.
